1. Why this project exists

The idea comes from your experience when your mother-in-law was sick and dying with cancer. Her hospital team provided great medical care, while family members worked together to make sure she was never alone and always had someone available to help.

CareRelay should make that coordination easier to see and easier to share. Someone arriving tired or worried should quickly understand who is there, who comes next, and what still needs attention.

Questions the page should answer

  • Who is scheduled to be with the patient now and next?
  • Where are the gaps in coverage?
  • What help is needed, and who has offered to do it?
  • What does the next caregiver need to know?
  • Who should I contact if plans change?

The initial focus is family and friend coordination. Paid caregivers, multiple patients, and clinical integrations can remain separate ideas until their needs become clearer.

2. A small first version

Start with one patient, one care circle, and a single HTML page. Use LocalStorage to preserve the working data in the same browser. The goal is to learn whether the workflow feels useful before investing in a shared system.

Area Proposed first behavior What it helps us learn
Today Show planned coverage, the next handoff, and open tasks. What people need to see first.
Care circle Add names, contact information, and a short relationship or role. How helpers identify and contact one another.
Coverage Add a start and end time, location, and assigned helper. Clearly label open periods. How the family arranges someone to be there.
Tasks Create practical requests such as bringing dinner or arranging a ride; assign and complete them. How responsibilities move from request to completion.
Handoff notes Record a short dated note with an author. Which information is useful to the next person.
Import / export Export the full working dataset to JSON and import a validated file. How to retain the prototype data and move it later.
LocalStorage has an important boundary: It belongs to a browser profile and origin. It does not synchronize family members' devices. This first version is a workflow prototype; shared coordination will require a backend. Exporting and importing a file is a manual transfer, not live collaboration.

For early exploration, use fictional people and notes. LocalStorage does not provide application-level access control or encryption. Browser clearing can remove the data. Keep exported backups, and establish access and privacy requirements before storing real patient information in a shared version.

A sample walk-through

Alex is scheduled from 8 a.m. to noon. Jordan takes noon to 4 p.m. The evening period is unassigned. Someone opens Today, sees the gap, assigns Sam, and adds a request to bring dinner. Before leaving, Alex records a practical handoff: “Phone charger is in the bedside drawer; Jordan is bringing lunch.”

A scheduled shift is a plan. It does not prove that someone has arrived. If actual presence becomes important, introduce a separate check-in rather than treating an assignment as confirmation.

4. Candidate information model

Use stable IDs so records reference one another without depending on a person's display name. Keep a schema version in exports so later versions can recognize and migrate older data.

Record Candidate fields
Project dataset schemaVersion, exportedAt, patient, caregivers, coveragePeriods, tasks, handoffNotes
Patient id, preferredName, careLocation, generalCoordinationNotes
Caregiver id, name, relationship, phone, email, active
Coverage period id, startAt, endAt, caregiverId (optional for an open period), location, status
Task id, title, description, assigneeId, dueAt, status, completedAt
Handoff note id, authorId, createdAt, text

Define the hours that actually need coverage before calculating gaps. An empty calendar outside those hours is not necessarily a problem. Store date-times consistently with timezone information and display them in the care location's timezone. Decide how overnight periods and overlapping helpers should behave.

Consider a namespaced storage key such as careRelay.data.v1. Keep storage operations separate from page rendering so the data source can change later. Imported JSON should be checked before replacing current data, with a backup or explicit replacement choice.

5. Grow when a need justifies it

Stage Purpose Reason to move forward
HTML + LocalStorage Try the workflow, forms, and schema with sample data. The basic page answers the core coordination questions.
React interface Organize increasingly complex views and reusable controls. Interface state and components become hard to maintain.
API + database Provide one shared source of data across devices. Multiple caregivers need current shared information.
Accounts and care circles Invite helpers and control who can view or change each circle. Real users and private information enter the system.
Notifications and history Help people respond to changes and see who changed a plan. Actual use reveals missed handoffs or unclear changes.

React and the backend are independent choices. React alone does not add sharing, and a plain HTML interface can use an API. A C# / ASP.NET Core API and SQL Server would fit your existing experience, but that choice can wait until the workflow is clearer.

Before a shared release, define invitation and access rules, authorization on each care circle, simultaneous edit behavior, backups, and data retention. If reminders are introduced, decide how to show delivery failures; a sent notification is not proof that someone accepted responsibility.

6. Questions for our next conversations

  • Is the main job continuous bedside coverage, occasional visits, practical tasks, or some combination?
  • Who organizes the care circle, and can any helper change the schedule?
  • Should people volunteer for open periods, or should someone assign them?
  • What happens when a caregiver cannot make it or is running late?
  • What information would you have wanted to see when arriving at the hospital?
  • Should the patient participate directly, and what preferences should guide the page?
  • What belongs in a handoff note, and what should stay with the medical team's records?
  • What is the smallest feature that would have helped your family that first week?

These are discussion prompts, not prerequisites. We can take one at a time and let your experience shape the answers.

7. When you are ready to start

  1. Choose one concrete family scenario and write what success looks like.
  2. Sketch the Today view and one form before adding more sections.
  3. Create a small fictional dataset with an open coverage period and an unassigned task.
  4. Build the smallest HTML / LocalStorage slice that completes that scenario.
  5. Add JSON import and export early so the evolving dataset stays portable.
  6. Walk through it as a tired caregiver on a phone, then adjust what feels confusing.
  7. Turn the next useful improvements into small PBIs with observable acceptance criteria.

Candidate first PBIs

PBI Example acceptance criterion
Maintain the care circle After adding a helper and refreshing, that helper still appears.
Schedule coverage A valid period shows its times and helper; an end before the start is rejected.
Show open coverage An unassigned period is clearly labeled “Needs someone.”
Share a practical task A task can be assigned and completed, and the changes survive a refresh.
Carry data forward An exported dataset can be restored; invalid input leaves the existing data intact.
